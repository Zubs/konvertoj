## Context

All features are built; CI passes on every system and Node.js version. The package has version `0.0.0` and no repository details. There is no release workflow. The regression runs of features 17–19 found three small issues against Spec.md's "Helpful" and "Safe" goals.

## Goals / Non-Goals

**Goals:** everything Features.md feature 20 lists, short of actually publishing: version, package details, release workflow with provenance, audit, the Spec.md goal check, and fixing what that check finds.

**Non-Goals:** publishing, creating the npm account or tokens, pushing the tag (the maintainer does these); recording the demo GIF (vhs can't run here); the portfolio write-up (the maintainer's own words); major upgrades of TypeScript or `@types/node`.

## Decisions

- **package.json.** `version: "1.0.0"`; keep the existing `description`; `keywords`: `["convert", "converter", "image", "heic", "jpg", "png", "webp", "avif", "pdf", "gif", "mp4", "mp3", "compress", "resize", "cli", "local", "private", "offline"]`; `repository: { type: "git", url: "git+https://github.com/Zubs/konvertoj.git" }`; `homepage: "https://github.com/Zubs/konvertoj#readme"`; `bugs: { url: "https://github.com/Zubs/konvertoj/issues" }`; `publishConfig: { access: "public", provenance: true }`. `--version` prints `1.0.0` because it already reads `package.json`.
- **Release workflow.** `on: push: tags: ["v*"]` and `workflow_dispatch`, with `concurrency: release`. One job on `ubuntu-latest`, `permissions: { contents: read, id-token: write }`. Publishing versus dry run is decided by the event, never by the ref, so a hand-started run with a tag selected can't publish. Steps: checkout; `actions/setup-node` with Node.js `24` and `registry-url: https://registry.npmjs.org`, without an npm cache (kept out of the publishing job as a supply-chain precaution); `npm ci`; for `github.event_name == 'push'`, the tag check straight away so a wrong tag fails in seconds: `expected="v$(node -p "require('./package.json').version")"; test "$expected" = "$GITHUB_REF_NAME" || { echo "The tag is $GITHUB_REF_NAME, but package.json says $expected."; exit 1; }`; `npm audit`; `npm run check`; `npm run build`; `node dist/cli.js --install-video`; `npm test`; `node scripts/update-readme.js --check`; then for `push`, `npm publish` with `NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}` (provenance and public access come from `publishConfig`), and for `workflow_dispatch`, `npm publish --dry-run`. npm's trusted publishing (OIDC) works with the same step once it is set up on npmjs.com, and then no token is needed; the first publish of a new package needs the `NPM_TOKEN` secret. Node.js 24 ships an npm new enough for both.
- **Audit in CI.** A `npm audit` step in the `check` job with `if: runner.os == 'Linux'`, after `npm ci`. `npm audit` exits non-zero on any finding.
- **Dependencies.** Run `npm update` for in-range updates (today: typescript-eslint 8.72.0 → 8.72.1), lockfile only. Not done: TypeScript 7 (a new compiler, a major change to the toolchain, needing its own checking) and `@types/node` 23+ (konvertoj supports Node.js 22, so its types must stay at 22). Both are recorded in Decisions.md.
- **displayPath.** A function in `src/paths.ts`: `displayPath(cwd, file)` returns `path.relative(cwd, file)` unless that is empty, starts with `..` followed by a separator or equals `..`, or is absolute (another drive on Windows); then it returns the absolute `path.resolve(file)`. Every place that shows a user a path with `path.relative(…)` uses it: `src/report.ts` (line and describe), `src/detect.ts` (errors and the left-out note), `src/main.ts` (dry-run lines), `src/output-files.ts` and `src/inputs.ts` (messages), `src/convert/colours.ts`, `src/convert/info.ts` and `src/convert/pdf-create.ts`. In `info` and `colorpick`, the `--json` `file` field uses it too, so a file outside the current folder gets an absolute `file`. The current folder itself, shown today as `.` in `output-files.ts` and `inputs.ts`, is now shown as its absolute path, and tests expecting `.` are updated. Output naming (`src/outputs.ts`) is not about display and is left alone. The other-drive case uses the platform's `node:path`, so its test runs only on Windows (`it.runIf(process.platform === "win32")`; CI runs it).
- **Combined items.** `checkItem` in `src/detect.ts` already returns only the usable inputs, and `runBatch` already passes them to `mode.run`. The bugs are in `src/runner.ts`, which still uses `item.inputs` after the check: the "before" size (`totalSize(item.inputs…)`), `reporter.succeeded({ ...item, output })`, and a failure after the check (`reporter.failed(item…)` and `result.failed.push({ item … })`, which also feed the summary's "Failed:" list). After a successful check, all of these use `{ ...item, inputs: checked }`. A failure in the check itself keeps the planned item. The "Working on …" line in `--verbose`, printed before the check, is left as it is.
- **Empty folders.** Where output folders are prepared (`prepareOutputFolders` in `src/output-files.ts`), `mkdir(folder, { recursive: true })` returns the top-most folder it created, or `undefined` if the folder existed. When it returns a folder, every folder from the output folder up to and including that one is recorded (so `-o out/pages` with neither existing records `out/pages` and `out`), across all output folders of the batch (`-r` included). `prepareOutputFolders` returns the recorded folders; if it fails part-way ("Can't write to …") it removes the ones it created before throwing. `runBatch` wraps the batch in `try/finally` and, at the end (success, failure, an unexpected error or the first Ctrl+C), removes each recorded folder, deepest first, with `rmdir`, ignoring errors, so a folder with anything in it is never removed and a folder that existed before is never recorded. A second Ctrl+C kills konvertoj at once and only removes the temporary files, as now; empty folders created by that run may stay. `--dry-run` creates nothing, as now.
- **Launch checklist.** `docs/launch-checklist.md` lists each goal of Spec.md section 2 with its evidence and an honest status: *met*, *met with an exception* (named) or *pending (maintainer)*. "Private": the only network use is the add-on download the user agrees to (feature 14's tests, and the code's only `fetch`). "Fast": the numbers measured during this work and the machine they were measured on (HEIC just under a second is said plainly). "Dependencies up to date": met with the TypeScript 7 and `@types/node` 23+ exception. "Portfolio-ready": pending (maintainer), since it needs the published package, the demo and the write-up. Every timing in it is measured while doing this feature, not copied. Then the maintainer's steps in order: (1) record the demo GIF with `npm run demo`, commit it and run `npm run docs`; (2) write the short write-up; (3) put today's date on the CHANGELOG's 1.0.0 heading and commit — this is the last commit before the tag; (4) check CI is green on every system for that commit; (5) create the npm account or log in, create a granular access token with read and write access and "bypass two-factor authentication" turned on, and save it as the `NPM_TOKEN` repository secret (without the bypass the first publish fails with EOTP); (6) run the release workflow by hand and check the dry run; (7) push the `v1.0.0` tag; (8) on npmjs.com, set up trusted publishing for `Zubs/konvertoj` and `release.yml`, then delete the token and the secret; (9) add the npm link (and badge, if wanted) to the README, now that the page exists; (10) check `npx konvertoj@1.0.0 --version` on a clean computer; (11) have someone else convert an iPhone photo using only the README; (12) tick "20. Launch readiness" in Features.md and update Spec.md's stage. It is linked from CONTRIBUTING.md.
- **README.** A link to the source on GitHub is added now (the page exists, so the online link check passes); the npm link and badge wait until the package is published (checklist step 9).
- **CHANGELOG.** `## Unreleased` becomes `## 1.0.0`, with a line saying the date is added in the last commit before the tag (checklist step 3).
- **CONTRIBUTING.** A "Releasing" section: run the release workflow by hand, then `git tag v1.0.0 && git push origin v1.0.0`, and the npm setup.

## Risks / Trade-offs

- The first publish needs a token; the workflow supports both a token and trusted publishing.
- The "under a second" goal for a phone photo is met on a recent Mac but close for HEIC; slower computers may take longer. The checklist states the measured numbers rather than claiming more.
