## Context

The `check` CI job runs the test suite from a checkout. Nothing tests the packed tarball as users get it. The FFmpeg download uses `fetch`, which on Node.js ignores `HTTPS_PROXY` unless Node.js's proxy support is switched on.

## Goals / Non-Goals

**Goals:** a clean-install smoke test on the five systems and three Node.js versions in Features.md; an install-size budget; a start-up time limit; proxy support for the download.

**Non-Goals:** publishing (feature 20); bundling or shrinking dependencies; testing Windows on ARM.

## Decisions

- **Runners.** `windows-latest`, `macos-15-intel`, `macos-latest` (Apple Silicon), `ubuntu-latest` and `ubuntu-24.04-arm`, each with Node.js `22`, `24` and `latest` from `actions/setup-node`. `fail-fast: false`.
- **The job.** Every step uses `shell: bash` (Git Bash on Windows), so commands and `$RUNNER_TEMP` paths read the same everywhere. Check out, set up Node.js (with `cache: npm`), `npm ci`, `npm run build`, then `npm pack --pack-destination "$RUNNER_TEMP"`; the tarball's path is `$RUNNER_TEMP/konvertoj-<version>.tgz`, with the version read from `package.json` by `node -p`. Then in an empty folder `$RUNNER_TEMP/install`: `npm init -y` and `npm install <tarball>`. Run `npx --yes <tarball> --help` from another empty folder, and check its output contains `Usage:`, to cover `npx`. Before packing, `npx vitest run test/ffmpeg.test.ts` runs the proxy tests on this Node.js version (the `check` job's Node.js 22 skips the runtime-proxy ones). Then `node scripts/install-size.js <folder>` and `node scripts/smoke.js <folder>`, which deletes its temp folder when it passes. The scripts are run from the checkout but only run the installed copy, `<folder>/node_modules/konvertoj/dist/cli.js`, never `dist/` from the checkout.
- **Smoke test (`scripts/smoke.js`).** Plain JavaScript (like `scripts/update-readme.js`), with only Node.js built-ins. It makes a temp folder `konvertoj smoke/my files`, copies `test/fixtures/iphone.heic` and `test/fixtures/clip.mov` in, and runs the installed CLI with `execFileSync(process.execPath, [cli, ...args])`, no shell:
  1. `--help` once to warm up, then five times; fail if the median is 500 ms or more.
  2. `-m heictojpg <absolute path>/iphone.heic -o <absolute path>/photo` → `photo.jpg` exists; from the work folder with a relative input too (`-m heictojpg my files/iphone.heic -o relative` with `cwd` set); and with no `-o` (`-m heictojpg iphone.heic` with `cwd` set to `my files`) → `iphone.jpg` beside it, the "friend on another system" journey.
  3. `-m topdf photo.jpg -o document` → `document.pdf` starts with `%PDF`.
  4. `-m togif photo.jpg -o still` → `still.gif` starts with `GIF8`.
  5. The video steps run with a reduced environment: `PATH` holds only the folder of `process.execPath` (plus `SystemRoot` kept on Windows), `HOME`, `USERPROFILE`, `LOCALAPPDATA` and `XDG_CACHE_HOME` point into the temp folder, so no FFmpeg installed on the runner or cached earlier is found. The script starts a local proxy (`node:http` server handling the `connect` event: it records the target, opens a `node:net` connection to it and pipes both ways) and sets `HTTPS_PROXY=http://127.0.0.1:<port>`, plus `NODE_USE_ENV_PROXY=1` only when its own Node.js (the same `process.execPath` that runs the CLI) has no `http.setGlobalProxyFromEnv`, so on Node.js 24 and latest the tunnel proves konvertoj's own call works and on Node.js 22 it covers the `NODE_USE_ENV_PROXY` route. `TEMP`, `TMP` and `TMPDIR` are kept. It runs `--install-video` and checks the proxy saw `github.com:443`. Then `-m movtomp4 clip.mov -o clip` → `clip.mp4` exists and isn't empty, and `-m togif clip.mov -o moving` → `moving.gif` starts with `GIF8`. These steps use `execFile` (not the synchronous form) so the proxy in the same process keeps working.
  6. `-m info photo.jpg --json` → parses as a JSON array whose first entry has a width.
  Each step prints a ✓ line; the first failure prints the command, exit code and output, and exits with code `1`. Paths are built with `node:path`, so they have backslashes on Windows.
- **Install size (`scripts/install-size.js`).** Walks `<folder>/node_modules` with `fs.readdir({ recursive: true, withFileTypes: true })` and adds up the sizes of regular files (symbolic links are not followed). Budget 150 MB: the clean install on macOS Apple Silicon is about 120 MB on disk; the platform binaries for sharp and @napi-rs/canvas differ by system, so the budget leaves room. An optional `--budget <MB>` argument exists so the test can check the failing case. Prints `Installed size: N MB (budget 150 MB)`; over the budget it prints `Installed size N MB is over the budget of B MB.` and exits with code `1`. The sizes printed by the first CI run on each system are recorded in Decisions.md.
- **Start-up.** Heavy libraries already load lazily (feature 2's import test). The smoke test adds the time limit on the installed copy.
- **Proxy.** Before the download's `fetch`, if `http.setGlobalProxyFromEnv` exists (Node.js 24.14+ and 25.4+), call it with the run's environment; with no proxy variable it changes nothing. Call the function it returns in a `finally` once the body has finished streaming, to restore the previous setting. The function is looked up on the `node:http` default export when the download runs, through a small typed check (`@types/node` 22 doesn't declare it), so tests can remove it to act as an older Node.js. If it throws (`ERR_PROXY_INVALID_CONFIG` or `UND_ERR_INVALID_ARG` for a value such as `proxy.corp:8080`), konvertoj fails with a `UserError`: "HTTPS_PROXY is set to proxy.corp:8080, which isn't a valid proxy address (it should look like http://proxy.example.com:8080). Fix or unset it." naming the first of `https_proxy`, `HTTPS_PROXY`, `http_proxy`, `HTTP_PROXY` whose value isn't a `URL` with an `http:` or `https:` scheme. Node.js 22.21+ also supports `NODE_USE_ENV_PROXY=1`, which switches the same support on at start-up. When a proxy setting is set, runtime support is missing and `NODE_USE_ENV_PROXY` isn't set, a connection failure adds: "konvertoj found a proxy setting, but this Node.js version only uses it with NODE_USE_ENV_PROXY=1 (Node.js 22.21 or newer). Set it, or update Node.js." No proxy code of our own and no new dependency. `NO_PROXY` follows Node.js's rules; the GitHub release address redirects to `release-assets.githubusercontent.com`, so excluding the download needs both hosts.
- **Proxy tests.** The local test proxy is a `node:http` server that handles the `connect` event (Node.js's `fetch` tunnels with `CONNECT` even to `http` addresses), records the target and pipes to it with `node:net`. Tests: with `HTTP_PROXY` set, the download from the local `http://127.0.0.1` source goes through the proxy and installs; with `NO_PROXY=127.0.0.1` it connects directly; with no setting it connects directly; with `HTTPS_PROXY` set and an `https://example.invalid` source, the proxy records `example.invalid:443`, answers 502 and the run fails with the connection message; `HTTPS_PROXY=proxy.corp:8080` fails with the invalid-address message. Those need the runtime API and are skipped without it. With the API removed from `node:http` for the test, a failed connection with `HTTPS_PROXY` set includes the `NODE_USE_ENV_PROXY=1` advice; this one runs on every Node.js version. The real download through a proxy also runs in every packaging job through the smoke test, including Node.js 22 with `NODE_USE_ENV_PROXY=1`.
- **Paths with spaces and backslashes** are covered by the smoke test on Windows, and already by the existing input tests.

## Risks / Trade-offs

- Fifteen jobs take runner time; they run in parallel and only use the packed tarball.
- The 500 ms limit could be close on a slow runner; the median of five warm runs keeps it stable, and today it is about 40 ms.
- `macos-15-intel` is the remaining Intel macOS runner; if GitHub removes it, the matrix needs updating.
